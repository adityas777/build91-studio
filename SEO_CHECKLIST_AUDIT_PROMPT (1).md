# Copy-paste prompt for another coding agent

## Role

Act as a senior technical SEO engineer and evidence-driven code auditor. Audit the supplied coded website against the complete Wix Step 1 and Step 2 SEO checklist defined in this prompt, then perform an extended technical SEO cross-check so important coded-site issues are not missed.

This is an **audit-first task**. Do not change code, content, infrastructure, DNS, analytics, Search Console, or production settings unless the user separately authorizes implementation. Do not mark a check as passed merely because a helper, plugin, framework, or CMS normally generates it.

## Portability rules

- Do not assume a framework, build tool, CMS, routing system, hosting provider, operating system, filename, repository layout, or project location.
- Discover the project's actual architecture before auditing it.
- Never include machine-specific or absolute paths in the report.
- If source locations are useful evidence, report only portable repository-relative locations and line numbers.
- Do not assume that the coded site has the same routes or pages as the Wix snapshot.
- Inventory the coded site's real public routes, then apply the page-level Wix checks to every relevant route.
- Treat the Wix page names and statuses as historical reference data, not as the coded site's required information architecture or current result.

## Inputs to establish

Determine these from the repository, deployment, configuration, and user-provided context. If an item cannot be discovered safely, list it as an explicit unknown rather than guessing.

- Brand or business name.
- Primary site purpose and conversion goals.
- Target audiences, services, products, locations, and markets.
- Approved target keywords or topic clusters, if any.
- Production domain and canonical host.
- Preview, staging, alternate, legacy, and localized domains.
- Framework, rendering model, build command, and route generation strategy.
- Public route inventory, including statically generated, server-rendered, dynamic, CMS-backed, and parameterized pages.
- Routes intentionally excluded from indexing, such as account, admin, checkout, preview, utility, filtered, search-result, or duplicate pages.
- Search Console, analytics, DNS, hosting, and production access that is actually available.

Do not fabricate keyword targets. The Wix snapshot showed the terms "3D architectural visualization," "Build91," "wedding visualization," "3D rendering," and "2d drawings," but only use them for the coded site if current project evidence or the user confirms they remain valid.

## Required audit method

Use both source-level and rendered-site evidence.

1. Read the project's agent instructions, documentation, configuration, route declarations, content sources, metadata helpers, layout or template code, image usage, navigation, robots rules, sitemap logic, and deployment configuration.
2. Build or run the project using its documented workflow. Do not invent commands. Preserve the user's existing work and do not start a duplicate development server if one is already running.
3. Create a complete public-route inventory. Reconcile routes found in code, generated route output, navigation, sitemap, robots rules, redirects, and a crawl of the rendered site.
4. Classify every route as `INDEXABLE`, `NOINDEX`, `REDIRECT`, `ERROR`, `PRIVATE/AUTHENTICATED`, or `UNKNOWN` and explain the basis.
5. Inspect the final rendered HTML or DOM for each representative route. Source declarations alone do not prove that metadata or content reaches the browser.
6. Test desktop and mobile renderings. Include at least one narrow mobile viewport and one desktop viewport.
7. Where practical, crawl both the canonical production origin and the locally built version. Separate production findings from local/source findings.
8. Record exact evidence for every conclusion. A passing check needs observable proof; a failing check needs the offending value or behavior; an unavailable check needs the missing access or evidence.
9. Do not edit the site during the audit. Finish with a prioritized remediation plan and wait for authorization before implementation.

## Result vocabulary

Use only these statuses:

- `PASS`: verified in source and/or rendered output with sufficient evidence.
- `FAIL`: verified missing, incorrect, broken, duplicated, misleading, or below the stated acceptance criteria.
- `PARTIAL`: implemented on some routes or only partly satisfies the acceptance criteria.
- `NOT APPLICABLE`: legitimately irrelevant, with a short reason.
- `NOT VERIFIED`: cannot be proven with the available access or environment.

Do not convert `NOT VERIFIED` into `PASS`. Do not let a site-wide default hide page-specific failures.

## Wix Step 1 audit: homepage readiness

Audit all seven Wix Step 1 requirements.

### 1. Homepage title for search results

Verify that:

- The homepage emits a non-empty HTML `<title>` in the rendered document head.
- The title is descriptive, unique, human-readable, and aligned with the page's real purpose.
- The brand and primary topic or offering are represented naturally when appropriate.
- The title is not only a development placeholder, raw URL, route name, filename, repeated keyword list, or generic word such as "Home."
- The title is not duplicated by another indexable page.
- Site-wide templates do not accidentally repeat the brand or separator.
- Dynamic metadata resolves correctly in the final HTML, including production builds.
- A practical display target is roughly 30-60 characters, but relevance and uniqueness take priority over a rigid character limit because search engines truncate by display width and may rewrite titles.

Report the exact rendered title and its character count.

### 2. Homepage description for search results

Verify that:

- The homepage emits one non-empty `<meta name="description">` in the rendered head.
- The description accurately summarizes the page, differentiates the business, and gives a useful reason to visit.
- It is written for people, uses relevant language naturally, and avoids keyword stuffing.
- It is not duplicated across indexable pages.
- It is not placeholder text, boilerplate, a navigation dump, or a mechanically truncated sentence.
- A practical target is about 120-160 characters, while acknowledging that search engines may choose a different snippet.

Report the exact rendered description and its character count.

### 3. Meaningful text on the homepage

Verify that:

- The homepage contains crawlable, visible HTML text explaining the business, main offerings, audience, and differentiators.
- Essential meaning is not available only inside images, video, canvas, animation, CSS-generated content, or client-side interactions that fail without JavaScript.
- There is one clear primary heading, and the heading hierarchy is logical.
- Main topics and approved keywords appear naturally in useful copy, without stuffing or hidden text.
- Important content exists in the initial or reliably rendered HTML and is not blocked behind consent, animation, or interaction.
- The page provides enough context for a search engine and a visitor to understand what the site offers and where it operates.

### 4. Homepage indexing allowed

Verify the complete indexing chain:

- The homepage returns a successful HTTP status.
- It is not blocked by `robots.txt`.
- It does not emit `noindex` through a meta robots tag or `X-Robots-Tag` header.
- Its canonical URL points to the intended canonical homepage and uses the canonical scheme and host.
- It is not trapped behind authentication, an interstitial, a redirect loop, a client-only shell, or an error-shaped success response.
- Preview, staging, duplicate, and alternate-host versions are not accidentally competing with the canonical production page.
- The sitemap and internal links use the canonical homepage URL.

### 5. Mobile optimization

Verify that:

- A valid viewport meta tag is present.
- Layout, navigation, text, forms, buttons, media, and interactive controls work on narrow screens.
- There is no material horizontal overflow, clipped content, overlapping text, unreadably small text, or inaccessible navigation.
- Tap targets and spacing are usable.
- Mobile content and metadata remain equivalent to desktop where search relevance depends on them.
- Images and video are responsive and do not cause avoidable layout shift.
- Important motion respects reduced-motion preferences.
- Mobile performance is evaluated with field data when available and lab data otherwise; distinguish the two.
- Core Web Vitals evidence covers Largest Contentful Paint, Interaction to Next Paint, and Cumulative Layout Shift when the required tooling or data is available.

### 6. Custom domain

Verify that:

- The production site uses the intended custom domain rather than only a temporary platform subdomain.
- HTTPS is valid and there is no mixed active content.
- HTTP redirects to HTTPS.
- Alternate `www` and non-`www` hosts resolve consistently to one canonical host.
- Redirects are direct and permanent where appropriate, without chains or loops.
- Canonical tags, sitemap URLs, structured data URLs, Open Graph URLs, internal links, and environment configuration consistently use the canonical origin.
- Old or alternate production domains do not expose duplicate indexable copies.

If DNS or hosting access is unavailable, verify public behavior and mark private configuration details `NOT VERIFIED`.

### 7. Google Search Console submission

Verify separately:

- Search Console property ownership or access.
- Correct property type and canonical production origin coverage.
- Homepage index status or URL Inspection evidence.
- Sitemap submission and latest processing result.
- Coverage or Page Indexing issues affecting the homepage.
- Manual actions and security issues, if access permits.

Repository code cannot prove Search Console submission. Without current Search Console access or exported evidence, mark this check `NOT VERIFIED` and provide the exact manual verification steps. Do not claim submission merely because a verification tag or sitemap exists.

## Wix Step 2 audit: every relevant site page

For every indexable route, and for every representative template behind dynamic routes, audit all four checks below. The homepage title and description are assessed in Step 1, but its image alt text and links remain Step 2 checks.

For intentionally non-indexable pages, still assess usability and accessibility where relevant, but clearly distinguish SEO requirements from accessibility requirements. A legal or utility page is not exempt merely because it is less commercially important.

### A. Search-result title on every page

For each page, verify:

- Exactly one meaningful rendered `<title>`.
- Unique value among indexable pages.
- Accurate match to the page's content and search intent.
- Natural inclusion of the page topic and brand where appropriate.
- Correct behavior for dynamic, CMS, paginated, localized, filtered, and parameterized pages.
- No accidental fallback to the homepage title.
- No duplicate brand suffix, unresolved token, placeholder, or environment label.
- Sensible display length, normally around 30-60 characters without treating that range as an absolute rule.

Provide a duplicate-title group report, missing-title report, and a full page/title inventory.

### B. Meta description on every page

For each page, verify:

- Exactly one non-empty rendered meta description.
- Unique, accurate, useful, and page-specific copy.
- Natural wording that supports likely search intent and click-through.
- No raw data, HTML fragments, unresolved template variables, keyword lists, or meaningless global boilerplate.
- Sensible display length, normally around 120-160 characters without treating that range as an absolute rule.
- Dynamic descriptions resolve for representative content entries and do not collapse to duplicates.

Provide missing, empty, duplicate, too-short, and unusually long description groups. Treat length as a quality signal, not an automatic failure when the copy is otherwise intentional.

### C. Alt text for all images

Inventory images from rendered pages and source usage, including responsive variants, lazy-loaded images, CMS images, remote images, CSS backgrounds that carry meaning, logos, icons, linked images, and images introduced after interaction.

Verify that:

- Informative images have concise, context-specific alternative text that conveys their purpose.
- Decorative images use an empty alt value or an equivalent accessible hiding technique, rather than noisy or redundant text.
- Linked images give the link an accessible name.
- Functional images describe the action or destination, not merely their appearance.
- Text embedded in an image is represented in accessible text when that text matters.
- Alt text does not start with redundant phrases such as "image of" unless context genuinely requires it.
- Filenames, IDs, URLs, generic words, and keyword stuffing are not used as alt text.
- Repeated images are handled according to their context rather than receiving misleading universal descriptions.
- Background images containing essential meaning have an accessible text alternative nearby.
- Video posters, galleries, carousels, lightboxes, and dynamically loaded media are included.

Do not fail decorative images for having `alt=""`. Do fail informative images with missing, empty, generic, or misleading alternatives. Report the page, image purpose, rendered alt value, and recommended correction for each issue.

### D. Links on every page

Verify that every important page participates in a crawlable and useful internal-link structure.

- The page contains at least one meaningful crawlable link where appropriate.
- Important navigation uses real links with valid destinations, not only click handlers, styled non-link elements, or script-dependent navigation.
- Anchor text describes the destination; flag repeated vague labels such as "click here" when context does not disambiguate them.
- Links have accessible names.
- Internal destinations do not return errors, loop, or create unnecessary redirect chains.
- Canonical internal URLs use the intended scheme, host, casing, trailing-slash convention, and locale.
- Orphan pages are identified by reconciling the route inventory, navigation, sitemap, and crawl graph.
- Policy, service, location, article, project, product, contact, conversion, and other relevant pages link to logically related destinations.
- Buttons used for navigation are evaluated as links; buttons used for actions remain buttons.
- `nofollow`, `ugc`, and `sponsored` values are used intentionally rather than applied indiscriminately to internal links.
- Fragment links target valid unique IDs.
- External links that open a new browsing context do so intentionally and safely.

Provide broken-link, redirected-link, orphan-page, empty-link, generic-anchor, and JavaScript-only-navigation findings.

## Extended coded-site SEO cross-check

The Wix Step 1 and Step 2 items are the minimum baseline. Also audit the following because a coded site can pass those visible tasks and still have material SEO defects.

### Route and crawl control

- Complete route inventory and crawl coverage.
- Correct `robots.txt` behavior for production and non-production environments.
- XML sitemap availability, valid XML, canonical absolute URLs, successful URLs only, appropriate segmentation, and accurate modification dates when supplied.
- Meta robots and `X-Robots-Tag` consistency.
- Canonicals that are absolute, self-consistent, and not pointed at redirects, errors, blocked URLs, or unrelated pages.
- Pagination, filters, parameters, search results, duplicate content, print views, and faceted navigation handling.
- No accidental indexation of preview, staging, admin, account, development, or duplicate-host content.

### HTTP behavior and URL quality

- Correct success, redirect, not-found, gone, and server-error status behavior.
- Real 404 responses for missing pages; no soft 404s or universal success shell.
- Direct permanent redirects for retired canonical URLs where appropriate.
- No redirect loops, excessive chains, inconsistent trailing slashes, duplicate casing, or duplicate query variants.
- Clean, stable, readable URLs without leaking implementation details or unnecessary parameters.

### Head metadata and sharing

- Correct character encoding and viewport declaration.
- One canonical title and description source per page without duplicate head tags.
- Open Graph title, description, URL, type, site name, and representative image.
- Twitter/X card metadata where the project intends social sharing.
- Absolute, accessible, correctly sized, fetchable share images.
- Favicons, web app icons, and manifest metadata where applicable.
- Search-engine verification tags are present only when needed and do not expose secrets.

### Content structure and quality signals

- One descriptive primary heading per page where appropriate.
- Logical heading nesting without using headings solely for visual styling.
- Clear crawlable copy matching each page's purpose and approved search intent.
- No hidden keyword blocks, doorway pages, copied boilerplate, thin duplicate pages, or placeholder content.
- Contact, organization, service, location, author, dates, policies, and trust information are accurate and consistent where applicable.
- Content rendered through JavaScript is present reliably in final output and does not disappear for crawlers or slow clients.
- Important content is not loaded only after scrolling or interaction without a crawlable fallback.

### Structured data

- Inventory all JSON-LD, microdata, or RDFa.
- Validate syntax and rendered values.
- Match schema types to visible page content and actual business facts.
- Use absolute canonical URLs and valid image URLs.
- Avoid fabricated ratings, reviews, prices, availability, locations, authorship, or business details.
- Check eligibility and required/recommended fields for each intended rich result.
- Ensure organization, website, breadcrumb, article, service, product, local business, FAQ, video, or other schema is used only when applicable.
- Record validation errors, warnings, and unsupported claims separately.

### Images and media

- Descriptive filenames where practical without breaking stable public URLs unnecessarily.
- Appropriate dimensions, responsive sources, modern formats, compression, and lazy loading.
- Do not lazy-load the likely Largest Contentful Paint image when doing so delays it.
- Explicit dimensions or reserved aspect ratio to limit layout shift.
- Captions and surrounding context where they improve understanding.
- Video titles, descriptions, thumbnails, transcripts or captions, and indexability where video search matters.

### Performance and mobile rendering

- Core Web Vitals and major contributing resources.
- Server response, render-blocking resources, JavaScript weight, hydration cost, fonts, third-party scripts, images, video, caching, and compression.
- Mobile-first content parity and responsive usability.
- Layout stability during font, image, video, animation, and client-component loading.
- Lab findings clearly separated from real-user field data.

### International and local SEO, when applicable

- Locale-specific canonical URLs and valid reciprocal `hreflang` clusters.
- Correct language and region codes plus `x-default` where appropriate.
- No automatic redirect that prevents crawlers or users from reaching alternate locales.
- Consistent business name, address, phone, service area, maps, and location landing-page facts.
- Do not assume local-business eligibility or physical offices without evidence.

### Security and trust signals with SEO impact

- HTTPS and no mixed content.
- No malware, hacked-content, deceptive-download, or security interstitial evidence.
- No secrets or private data exposed in metadata, structured data, source maps, or public configuration.
- User-facing policy, contact, attribution, and consent surfaces are reachable where applicable.

## Severity and prioritization

Assign each verified gap one priority:

- `P0`: widespread deindexing, production outage, malicious compromise, or another issue preventing the site from being safely discovered.
- `P1`: major indexation, canonicalization, crawl, rendering, broken-site, or site-wide metadata problem.
- `P2`: page-level relevance, duplicate metadata, missing alt text on important images, weak internal linking, structured-data error, or material mobile/performance problem.
- `P3`: localized polish, optimization opportunity, warning, or low-impact inconsistency.

Prioritize by impact, confidence, affected page count, and implementation risk. Do not call every checklist miss critical.

## Evidence rules

- Separate verified facts, inferred risks, hypotheses, and unknowns.
- Quote exact rendered values for titles, descriptions, robots directives, canonicals, headings, alt text, and relevant response behavior.
- Include response codes and redirect destinations where relevant.
- State whether evidence came from source inspection, local rendered output, production rendered output, public crawl, Search Console, field data, or lab tooling.
- Never claim Search Console submission, indexing, DNS correctness, production parity, or Core Web Vitals field performance without current evidence from the appropriate system.
- Sampling is allowed only for large dynamic sets. Document the sample method, template coverage, total known population, exceptions, and residual risk.
- If the crawl is blocked, incomplete, or limited to navigation-discoverable pages, say so explicitly and do not present it as sitemap-authoritative coverage.

## Final report structure

Return a detailed Markdown report in this order:

1. **Executive verdict**: concise answer on whether the coded site meets the Wix Step 1 and Step 2 baseline.
2. **Scope and environment**: code revision or build state, local/production targets, access used, route count, and audit limitations.
3. **Coverage reconciliation**: routes from code, navigation, sitemap, and crawl; explain differences.
4. **Wix Step 1 results**: seven-item evidence table.
5. **Wix Step 2 results**: full page/template coverage table for title, meta description, image alt text, and links.
6. **Extended technical SEO findings**: ordered by priority and confidence.
7. **Passed checks**: important verified strengths, kept brief.
8. **Unknowns and external checks**: Search Console, DNS, analytics, field data, production settings, or credentials that were unavailable.
9. **Prioritized remediation plan**: exact desired outcome, affected surfaces, dependencies, risk, and post-fix verification for every action.
10. **Final checklist totals**: `PASS`, `FAIL`, `PARTIAL`, `NOT APPLICABLE`, and `NOT VERIFIED`, with the denominator clearly stated.

## Completion gate

Do not call the audit complete until:

- All seven Wix Step 1 tasks have an evidence-backed status.
- Every discovered indexable page or representative dynamic template has title, meta description, image alt text, and link results.
- The route inventory has been reconciled against code, navigation, sitemap, redirects, and crawl evidence as far as available.
- Production and local/source conclusions are clearly separated.
- The 42-task Wix snapshot has been preserved as historical reference but not confused with the coded site's result.
- Unknown or inaccessible external checks are explicitly marked `NOT VERIFIED`.
- Every failure has a concrete, testable remediation and a post-fix verification method.
- No machine-specific path or assumed project layout appears in the final report.

End with a direct verdict in this form:

> **Verdict:** The coded site [meets / partially meets / does not meet] the Wix Step 1 and Step 2 SEO baseline. [Number] requirements pass, [number] fail, [number] are partial, [number] are not applicable, and [number] could not be verified. The highest-priority gaps are: [brief list].
